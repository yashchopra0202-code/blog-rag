# blog-rag — Daily Nuggets Design Spec

**Date:** 2026-09-05
**Status:** Approved (brainstorming), pending implementation plan
**Builds on:** `2026-09-04-blog-rag-design.md` (the base scrape → index → `/ask` system)

## Goal

Turn blog-rag from a question-answering tool into something used **daily**: it
pulls new posts from more first-party AI-lab blogs, compresses each new post into
a short "nugget" (a 2-3 sentence summary card), and puts those nuggets in front
of the user through two surfaces — a **"Today" web feed** and a **daily email
digest** — refreshed automatically each morning.

This is additive. The existing scrape → ingest → `/ask` pipeline is unchanged in
purpose; the new work is a summarization stage, a feed endpoint + view, an email
digest, more sources, and a scheduled runner.

## Scope decisions (settled during brainstorming)

- **Nugget format:** a **summary card** — site label, title, a 2-3 sentence
  "what happened → why it matters" blurb, and a source link. (Not a one-line
  takeaway; not headline+bullets.)
- **Consumption surfaces:** **both** a web "Today" feed (home base) and a **daily
  email digest** (the habit trigger that links back to the feed).
- **New sources:** **first-party lab/company blogs only.** No open news sites,
  aggregators, or newsletters — this deliberately preserves the existing trust
  boundary (see Security).
- **Freshness:** **scheduled daily**, run in **GitHub Actions** (cloud cron), not
  on the local Mac.
- **Email transport:** **Resend** (HTTP API via the already-present `httpx`); no
  new pip dependency.
- **Summarization model:** reuse `claude-haiku-4-5` (already configured for
  `/ask`); cheap and consistent.

## Design fork resolved: nugget generation & storage

Nuggets are generated by a **dedicated, incremental `nuggetize.py` step** and
stored **in `manifest.json`** (a new `nugget` field per URL), NOT in the article
`.md` files and NOT generated on-the-fly at request time.

Rationale:
- `api.py` already reads `manifest.json` for `/stats` and `/articles` without
  loading the vector index. Storing the nugget there means the entire "Today"
  feed serves from one cheap `json.load` — the expensive Chroma index stays
  reserved for `/ask`.
- Nugget generation summarizes each article's raw body directly and does **not**
  need the vector index, so it is independent of `ingest.py` and testable alone.
- Incremental by the same manifest pattern the scraper uses: only articles
  without a `nugget` field are summarized, so re-runs (and prompt tweaks) are
  cheap and never force an index rebuild.

Rejected: storing in article frontmatter (forces per-request file re-parse);
lazy generation at request time (repeated LLM cost, slow pages).

## Pipeline (daily order)

```
scraper.py    -> data/articles/*.md + manifest.json      (fetch new posts; incremental)
nuggetize.py  -> manifest.json (+ nugget, nugget_at)     (summarize new posts; incremental)  [NEW]
ingest.py     -> chroma_db/                               (rebuild index for /ask)
digest.py     -> Resend email                             (email the recent nuggets)          [NEW]
```

`ingest.py` runs in the daily order so `/ask` stays current, but the feed and the
email depend only on the manifest, not on Chroma.

## Components

### `nuggetize.py` (new)
- Load `manifest.json`. For each entry that has an article file but no `nugget`,
  read the article body, call `claude-haiku-4-5` with a fixed prompt, and write
  `nugget` (plain text, 2-3 sentences) + `nugget_at` (ISO timestamp) back to the
  entry. Save the manifest after each success (checkpoint), mirroring the
  scraper's per-item save.
- Prompt (fixed): summarize as 2-3 sentences — first what the post is / what
  happened, then why it matters — plain text, no preamble, no markdown.
- Isolation: a failure on one article logs a warning and continues; the entry
  simply stays without a nugget and is retried next run.
- Interface: `nuggetize_manifest(manifest, articles_dir, llm) -> int` (count
  written), so tests can pass a fixture manifest and a mocked llm.

### `manifest.json` (extended)
Per-URL entry gains two optional fields:
```
"nugget":    "<2-3 sentence summary>",
"nugget_at": "2026-09-05T13:00:00Z"
```
Existing fields (`title`, `date`, `site`, `file`, `scraped_at`) are unchanged.
Absence of `nugget` means "not summarized yet".

### `api.py` (extended)
New read-only endpoint:
- `GET /feed?days=7` → read the manifest; keep entries that have a `nugget` and
  whose `scraped_at` date falls within the last `days`; group by `scraped_at`
  date (newest day first); within a day, preserve manifest order (scrape order).
  Return `{days, groups: [{date, items: [{title, url, site, label, nugget}]}]}`
  where `label` comes from the existing `SITE_LABELS` map and `title` from the
  existing `nice_title` fallback.
- `days` clamped to a sane range (e.g. 1-30). No vector index load.

`/ask`, `/stats`, `/articles`, `/` are unchanged.

### `static/index.html` (extended)
Add a **"Today" view** to the existing page (same visual system, no build step):
dated sections, each a list of summary cards (site label · title · nugget ·
"read source" link), newest day first. The existing discovery/ask UI stays; the
feed is an added view, not a replacement. Empty state when no nuggets in range.

### `digest.py` (new)
- Read the manifest; select entries with a `nugget` scraped since the last
  digest (tracked by a small `data/digest_state.json` holding `last_sent`, an
  ISO timestamp — falls back to "last 24h" if absent).
- Build a simple, inline-styled **HTML email**: a header line (count + date), one
  block per nugget (title linked to source, site label, nugget text), and a
  footer linking back to the feed.
- Send via **Resend** HTTP API using `httpx`, `RESEND_API_KEY`, from a configured
  sender to `DIGEST_TO`. On success, update `last_sent`.
- If there are zero new nuggets, send nothing (and don't advance `last_sent`).
- Interface split for testability: `build_digest(entries) -> (subject, html)`
  pure/deterministic (tested against a fixture), and `send_digest(...)` doing the
  Resend call (mocked in tests).

### `sites.py` (extended)
Add first-party lab/company blogs. Candidates (exact `article_url_pattern` and
`render_js` to be confirmed against each live site during implementation, as was
done for the original set):
- xAI, Stability AI, Allen AI (AI2), Nvidia (research/generative-AI blog),
  Together AI, Perplexity, Qwen/Alibaba.

Each is one config entry — same four keys (`name`, `listing_urls`,
`article_url_pattern`, `render_js`) — and gets a `SITE_LABELS` entry in `api.py`.

### `.github/workflows/daily.yml` (new)
- Trigger: `schedule` cron (daily, ~13:00 UTC) + `workflow_dispatch` for manual
  runs.
- Steps: checkout; set up Python 3.12; install `requirements.txt`; install
  scrapling + its browser runtime (for `DynamicFetcher`); run `scraper.py` →
  `nuggetize.py` → `digest.py`; then commit updated `data/articles/*.md` and
  `data/manifest.json` (and `data/digest_state.json`) back to the repo.
- Secrets: `ANTHROPIC_API_KEY`, `VOYAGE_API_KEY`, `RESEND_API_KEY`, `DIGEST_TO`.
- **CI does not build or commit `chroma_db`** — a binary sqlite store would bloat
  the repo and produce unreadable diffs. The index is rebuilt locally with
  `ingest.py` on demand; neither the feed nor the email needs it.

### `.env.example` (extended)
Add `RESEND_API_KEY=` and `DIGEST_TO=`. (`DIGEST_FROM` if Resend requires an
explicit verified sender; otherwise a default.)

## Data flow

```
[GitHub Actions, daily]
  scraper.py --> data/articles/*.md, manifest.json
  nuggetize.py --> manifest.json (nugget, nugget_at)
  digest.py --> Resend --> user's inbox ; updates digest_state.json
  git commit data/ back to repo

[local, on demand]
  git pull
  uvicorn api:app --> browser:
     "Today" feed  <- GET /feed (manifest only)
     ask a question <- POST /ask (needs local `ingest.py` rebuild of chroma_db)
```

Email is the always-on daily push. The web feed is served locally after a pull
and reads the committed manifest, so it is fresh without a rebuild. Only `/ask`
needs a local `ingest.py` run.

## Error handling

- **nuggetize:** per-article isolation (warn + continue, leave un-nuggeted for
  retry); missing `ANTHROPIC_API_KEY` fails fast via `require_env`.
- **/feed:** missing/corrupt manifest → empty feed (200 with empty groups), same
  defensive read as `/stats` and `/articles`; `days` out of range → clamped.
- **digest:** zero new nuggets → no send, no state change; Resend error → non-zero
  exit + logged, `last_sent` NOT advanced (so the next run retries the same set).
- **CI:** each site already fails in isolation in the scraper; a whole-step
  failure fails the job visibly. `workflow_dispatch` allows manual re-run.

## Testing

- **`nuggetize`:** incremental skip (entries with a nugget are not re-summarized),
  manifest write shape, per-article failure isolation — LLM mocked, no network.
- **`digest`:** `build_digest` against a fixture manifest → expected subject +
  HTML contains each nugget and source link; "zero new" → no send; `send_digest`
  Resend call mocked.
- **`/feed`:** day grouping, `days` filter + clamp, only-nuggeted entries
  included, label/title fallback — against a fixture manifest, no index.
- Same pytest layout/style as the existing suite. The scraper venv still runs the
  scraper/extraction tests; the RAG venv runs the rest.

## Security / trust boundary

The `/ask` endpoint and the nugget summaries both feed raw third-party article
text to the LLM, so the system trusts the content of configured blogs. Adding
**first-party lab blogs only** keeps that boundary where the base design put it.
Do not add open news sites, aggregators, or user-submitted feeds without
revisiting this assumption. Nugget text is model output over trusted-source input
and is rendered into HTML (feed + email) — escape it on output to avoid injection
via a compromised source page.

## Risks

1. **Scraping JS-heavy sites from GitHub Actions may hit bot walls.** Most sites
   use `render_js=True` (`DynamicFetcher`, a headless browser). Cloud CI IPs are
   challenged (e.g. Cloudflare) more than a residential Mac IP, so some labs may
   fail to scrape from CI. The scraper isolates per-site failures, so it degrades
   rather than crashes. **Validate this first in implementation.** Fallback if
   unreliable: run `scraper.py` on the Mac (launchd) and let CI do only
   `nuggetize` + `digest` + commit.
2. **Trust-boundary drift:** future "more sources" requests must not silently
   include untrusted origins (see Security).

## Out of scope (YAGNI)

- News sites, aggregators, newsletters, arXiv, user-submitted feeds.
- Per-user accounts, multiple recipients, subscription management.
- Committing/serving the vector index from CI; always-on hosted web feed
  (local `uvicorn` after `git pull` for now).
- Personalization/ranking of nuggets, topic clustering, dedup across labs.
- Push notifications, mobile app, RSS output.
